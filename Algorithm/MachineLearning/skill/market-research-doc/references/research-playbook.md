# 调研执行手册

## 来源清单确认 Gate

完成初轮桌面研究后、撰写正文前，必须先向用户提交“本次资讯来源清单”。未经确认或明确授权，不进入正文。

清单格式：

| 序号 | 实践簇 | 来源类型 | 组织/项目 | 标题 | URL | 发布日期/访问日期 | 拟支撑结论 | 交叉验证与置信度 |
|---|---|---|---|---|---|---|---|---|
| S1 | 腾讯实践 | QCon | 腾讯云 | CubeSandbox 实践 | https://... | 2026-10 / 2026-10-27 | Agent 执行环境规模化 | 与 GitHub 仓库交叉验证，高 |

提交清单时同时说明：

- 本清单覆盖哪些实践簇，是否有某簇不适用及原因
- 哪些来源来自用户提供，哪些来自公开检索
- 哪些结论已有两个独立来源，哪些仍需核验
- 计划如何在正文使用：事实、生产经验、实现依据或背景

用户确认后再写作。用户要求增删时，更新清单并保留确认日期与增删记录；写作中新增来源可补充到第五章，但不得静默替换已经确认的实践簇。

## 行业实践来源矩阵

行业现状默认按以下六个实践簇检索与撰写，每簇至少保留 2 个可追溯来源。优先“1 个一手来源 + 1 个独立验证”；主题确实不适用时必须逐项写明，不得静默省略。

| 实践簇 | 必须回答 | 优先来源 |

## 实践簇五段证据矩阵

每个实践簇必须建立下表，不得只在段落中笼统描述。`规划` 是高风险字段：只接受有日期和来源的公开路线图；没有公开信息时写“未公开/待确认”，另列的“报告建议”必须明确是本报告建议，不得冒充厂商计划。

| 字段 | 必须回答 | AI Code Review 主题的最低证据 | 缺证据写法 |
|---|---|---|---|
| 背景 | 组织/产品、目标用户、采用动因、触发场景、时间范围 | 说明为什么需要评审自动化或上下文增强 | 未公开/待确认 |
| 问题 | 原流程痛点、约束、目标和边界 | 评审吞吐、人力、误报、上下文缺失、文档—代码漂移等 | 未公开/待确认 |
| 方案 | 产品边界、部署/集成形态、架构、上下文、权限、人机责任 | 代码平台/IDE 接入、增量评审、证据链、风险路由和文档关联 | 未公开/待确认 |
| 效果 | 指标、口径、基线、时间范围、归因和验证方 | 等待时间、首条有效意见、可行动命中率、误报/漏检、采纳率、返工/缺陷逃逸 | 未公开/待确认；不能用 stars 代替 |
| 规划 | 厂商公开路线图或组织已公布下一步 | 必须写来源日期；独立建议另标“报告建议” | 未公开/待确认 |
| 局限与适用边界 | 成本、成熟度、数据/合规、模型、权限和适用仓库 | 标注企业自报、样本局限、不能替代人工的判断 | 未公开/待确认 |

每个字段都应记录来源、发布日期/访问日期和置信度。一个实践簇至少两条来源不代表每个字段都已被验证；用“主张—来源”表检查字段覆盖率。

## 用户指定范围优先级

用户点名的厂商、项目或实践簇优先于默认六簇。保留用户指定集合，说明与默认六簇的映射、增删和原因；只有用户没有指定对象时才使用默认六簇补全。无法获得直接证据时，保留对象并按六字段逐项写“不适用/公开证据不足”，不得静默替换。

先建立“实践簇清单”，区分厂商、产品和子实践；例如阿里巴巴必须分别检查淘天/天猫、蚂蚁和开源项目，只有证据确实相同且合并理由写明时才可合并。每个清单项都要映射到六字段证据矩阵和图片/无图记录。

## 来源优先级

1. 用户提供的内部材料（明确标注“用户提供”、提供日期与责任人）
2. 官方文档、规范、架构白皮书
3. 大厂工程博客与生产实践（字节、阿里、天猫、蚂蚁、腾讯、OpenAI、Anthropic、Google、Meta、Netflix、Uber、华为、CNCF 项目博客）
4. GitHub 仓库本身（star、贡献者、发布节奏、issue 响应、license、生产案例）
5. 基准测试、论文、会议分享（含 QCon 等工程会议）
6. 第三方分析报告（只作背景，不作为技术证据）

## GitHub 高 star 实践检索

除了按主题搜索全站仓库，还要按组织定向检索，避免只看到通用框架而漏掉大厂真实实践。至少覆盖：

- 阿里巴巴/蚂蚁：`org:alibaba agent`、`org:antgroup agent`
- 腾讯：`org:Tencent agent`、`org:TencentCloud agent`
- 字节跳动：`org:bytedance agent`、`org:coze-dev agent`
- Codex：`org:openai codex`
- Anthropic：`org:anthropics claude`
- 其他：美团、网易、快手、小红书相关官方组织或公开工程账号

筛选顺序：star 排序发现候选 → 检查近 6 个月活跃度与 release → 阅读 README/架构文档 → 查 issue/PR 与生产案例 → 记录 license 和风险。star 不可单独作为技术优劣证据；低 star 但属于大厂官方仓库的项目可作为 QCon 或官方文档的补充证据，但必须说明其成熟度限制。

## QCon（InfoQ）探索

QCon 是 InfoQ 主办的技术大会，议程、Track 与演讲页可作为中文工程实践与生产案例来源，适合智能研发、平台中间件、可观测、架构演进等主题。

**入口与 URL 规律**：

- 官网首页：https://qcon.infoq.cn/
- 届次日程：`https://qcon.infoq.cn/<year>/<city>/schedule`
  - 例：2026 上海 https://qcon.infoq.cn/2026/shanghai/schedule
  - 往届同样适用：2025 北京/上海、2024 上海等
- Track：`https://qcon.infoq.cn/<year>/<city>/track/<id>`
- 演讲详情：`https://qcon.infoq.cn/<year>/<city>/presentation/<id>`

**探索步骤**：

1. 先看目标届次的 schedule，按主题/关键词筛选候选 session，记录标题、讲者、公司、Track、年份与城市。
2. 打开 presentation 页，提取摘要、关键架构、量化指标、落地规模与踩坑；如有 PPT/视频，记录链接。
3. 优先采用大厂生产实践与有量化数据的 session；厂商软文式分享只作线索，不作技术证据。
4. 关键结论至少与官方文档或第二个独立来源交叉验证。
5. 引用时写明 session 标题、讲者/公司、届次（年/城市）与访问日期。
6. 2026 上海优先检查 <https://qcon.infoq.cn/2026/shanghai/schedule>；若没有 Codex、Anthropic 等对象的专属议题，明确写“QCon 未发现专属议题”，改用官方文档、GitHub 和第三方采用证据，不得把提到某产品的其他公司议题包装成该产品的实践。

**限制**：QCon 演讲以经验分享为主，版本与时效性需核对；部分内容需登录或仅现场可见。不要把议程标题当作已证实的技术结论。

## 图片获取

- 优先官方文档中的 architecture diagram、comparison matrix
- 下载后确认文件可打开、分辨率足够、图中文字可读
- 记录：原图 URL、获取日期、license/使用条款
- 下载失败：保留外链 + 图注（说明"原图见链接"）
- 不摆放来源不明的图；不用生成图冒充官方架构图；自绘图必须标注"自绘"
- **图注格式**：每张图统一为 `图 <章节号>-<序号>：<标题>`；章节号取图所在最小小节编号（如 2.1.2），序号在该小节内从 1 递增
- **Markdown 呈现**：除 Mermaid 外，图片默认用 `[图注](本地相对路径)` 链接放入正文，相对路径优先按工作区根目录书写（如 `docs/research/images/<topic>/xxx.png`）；若用户要求预览可见，则用内嵌图片 `![图注](images/<topic>/xxx.png)`。两者都不使用绝对路径；只有下载失败时才使用远程外链并标注“原图链接”。Mermaid 用 `mermaid` 代码块直接渲染
- 每个有直接证据的实践簇至少配 1 张与该簇五段内容直接相关的代表性图片；代表性图片包括官方架构图、流程图、产品界面、部署图或原文生产实践图，不包括 logo 或通用装饰图。若无可公开复用图片，必须写“暂无可公开复用图片”、保留原文链接并说明原因；不得用一张图覆盖多个厂商的事实主张。
- 图片清单增加“所属实践簇、支撑字段/主张、来源、获取日期、许可”列；图片不能证明正文没有明确写出的结论。

## 参考链接整理

- 正文保留内联引用，所有来源统一汇总到第五章“参考链接”。
- 按六个实践簇分组：阿里巴巴（含天猫、蚂蚁）、腾讯、字节跳动、Codex、Anthropic、其他实践；另列内部与用户提供材料、图片与版权、来源核验记录。
- 每条来源保留标题、URL、发布日期或访问日期、来源类型和使用位置；用户提供材料注明“用户提供”。
- 图片注明路径、来源、获取日期和版权/许可。
- 来源核验记录写明来源清单确认日期、用户增删意见和后续新增来源。
- 不在前四章末尾重复列“本章来源”或其他分散来源清单。

## Skill 维护请求

当用户要求修改或同步本 skill 时，先检查 `SKILL.md` 及其引用的模板、清单和研究手册，再同步修改相关文件，验证交叉引用、章节约束和质量检查项一致，并在交付中列出文件变更与验证结果。纯 skill 指令修改不需要重新执行报告来源确认 Gate；同一请求若还要求改报告，报告部分仍需遵守来源确认 Gate。
