# 市场调研文档撰写

以技术平台架构师口吻，为技术管理者与落地团队写作，聚焦架构、容量、演进、运维成本和组织适配。默认产出 `docs/research/YYYY-MM-DD-<topic>.md`，图片放在文档同级 `images/<topic>/`。所有公开结论可追溯；内部底稿保留材料来源属性、日期和责任人，公开稿按公开披露边界处理。

## 工作流

### 1. 澄清调研简报

读取 [澄清清单](references/clarification-checklist.md)，一次提出 5-8 个关键问题，覆盖决策、范围、现状材料、输出和否决项。

**完成标准**：决策与读者、第四章模式（多方案选型或指定基础方案的总体方案）、主题边界、华泰现状材料、公开范围、输出要求、约束与否决项、用户指定的实践对象均有明确答复。若用户授权“按你的假设先写”，把假设、受影响结论和待确认责任人写入正文 1.3 节。

### 2. 研究并确认来源 Gate

读取 [调研执行手册](references/research-playbook.md) 和 [行业来源基线](references/industry-source-baseline.md)，先完成桌面研究，再提交来源清单。

- 用户点名的厂商或对象优先。AI Code Review 与 Agent 主题默认覆盖六簇：阿里巴巴（含天猫、蚂蚁）、腾讯、字节跳动、Codex、Anthropic、其他实践；其他技术主题按决策问题建立 4-6 个同等级实践簇，并在 2.1.0 说明映射。
- 每个有直接证据的实践对象至少使用 2 个可追溯来源，优先“一手来源 + 独立验证”。一个汇总簇不能用一个对象的来源覆盖其他子实践；不同的厂商、产品或子实践分别成条。
- 每个实践对象写一张六段实践卡：**背景 → 问题 → 方案 → 效果 → 规划 → 局限与适用边界**。每字段记录主张、来源、发布日期或访问日期、置信度；缺证据时写“未公开/待确认”。
- AI Code Review 的效果优先核对评审吞吐、等待时间、首条有效意见、可行动命中率、误报/漏检、采纳率、返工或缺陷逃逸，并记录口径、基线、时间范围和归因边界。
- 按执行手册的模板提交“本次资讯来源清单”，等待用户确认、删减或明确授权跳过。

**完成标准**：来源清单已获确认或明确授权跳过；每个有直接证据的实践对象有至少 2 个候选来源或逐项说明“不适用/公开证据不足”；GitHub 高 star 项目已评估，QCon 检索结果（含空结果）已记录；未覆盖字段和待核验结论已列明。

### 3. 撰写五章正文

按 [文档模板](references/document-template.md) 写作。一级章节只保留：**背景 / 现状 / 需求 / 方案选型（或方案） / 参考链接**。

- 背景交代演进脉络、量化问题和本次决策目标。
- 现状先列 2.1.0 实践簇清单，再按六段实践卡展开；行业总述不能替代各簇自己的背景与问题，架构描述不能替代效果，规模数字不能替代效果。
- 每个实践卡保留全部六个字段。无直接证据时逐项写“不适用/公开证据不足”并说明原因，不静默省略。规划区分“公开规划 / 报告建议 / 未公开或待确认”。
- 华泰现状只使用用户材料或可查证信息；缺失处写“待补充/需确认”，并写明谁提供什么。
- 需求写用户场景、触发条件、流程、成功标准和 P0/P1/P2；非功能约束单列。
- 第四章按决策类型二选一：需要比较多个候选时采用“选型模式”，至少比较自研、采购、开源改造等 3 个方案并统一打分；用户已指定基础方案时采用“方案模式”，写总体设计、预验证/影响分级、上下文供给、多 Agent 审查、修复追踪、集成落地，并保留风险与验证计划。
- 所有来源集中到第五章；正文保留内联引用，不在各章末尾重复列来源。
- 公开分享稿不出现“据用户提供/内部材料显示”等提交方式；内部底稿保留真实来源属性，内部事实先确认公开授权，否则改为中性表述、标待核验或移除。

**完成标准**：五个一级章节齐全；实践簇清单、六段实践卡、行业对比、华泰现状、场景化需求和第五章来源均完成；第四章按所选模式完成（选型模式含三方案评分与推荐，方案模式含总体设计和验证计划）；事实、推断和建议已分开表述。

### 4. 配对代表性图片

每个有直接证据的实践簇至少配 1 张与其六段内容直接相关的代表性图片，优先官方架构图、流程图、产品界面、部署图或原文实践图。

- 可公开复用的图无法获取时，使用标注“自绘”的架构图或证据关系图；仍无法形成有依据的图时，写“暂无可公开复用图片”并保留原文链接。
- 不使用 logo、通用装饰图，也不让同一张图冒充多个厂商的证据。
- 除 Mermaid 外，图片保存到文档同级 `images/<topic>/`，正文与第五章都使用从文档所在目录解析的相对路径。用户要求预览可见时用内嵌图片，否则默认用链接。直接给出远程图片 URL 时也要下载到本地，并用 `file`/`sips`/PIL 识别真实格式后转换；不直接 hotlink。
- 若 Markdown→HTML 构建器不支持 Mermaid，改用本地 SVG 自绘并标注“自绘”。小节增删或重排后重算图号，删除孤儿图片引用和第五章对应条目。
- 每张图使用 `图 <章节号>-<序号>：<标题>` 图注；来源、获取日期、许可和支撑主张写入 5.8。

**完成标准**：每个有直接证据的实践簇都有配对图片或明确的无图说明；所有图片路径可打开；图注连续且重排后已重算；孤儿引用已清理；图片与来源、许可、主张可互相回溯。

### 5. 交付自检

按 [质量自检清单](references/quality-checklist.md) 逐项核对，修复后再交付。

**完成标准**：全部检查项通过；第四章模式与用户决策一致；公开稿来源披露和统计口径已核验；若存在 MD→HTML 构建脚本，已重跑并验证标签闭合与图片路径；无法解决的缺口在正文明确标注；若本次请求同时修改 skill，列出改动文件和验证结果。

## 写作风格

- 先结论后论据，避免营销形容词。
- 能量化就量化：QPS、规模、延迟、成本、人力。
- 明确区分事实、推断和建议；推断写出依据。
- 正文引用使用 `[来源](URL)`，全部来源统一汇总到第五章。
- 篇幅未指定时默认 3000-5000 字，先给结论摘要，再逐章展开。

## Skill 维护请求

修改或同步本 skill 时，先检查 `SKILL.md` 和全部 `references/`，同步更新受影响的模板、清单和研究手册，验证交叉引用、章节约束、六段实践卡和质量检查项一致，并在交付中列出修改文件与验证结果。纯 skill 指令修改不触发报告来源确认 Gate；同一请求若还要求改报告，报告部分仍遵守来源确认 Gate。
