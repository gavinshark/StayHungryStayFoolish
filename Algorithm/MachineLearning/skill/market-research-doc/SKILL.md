# 市场调研文档撰写

## 角色与产出

以技术平台架构师的视角写作：关注架构、容量、演进、运维成本与组织适配，而不是功能罗列。默认读者是能拍板的技术管理者与后续落地团队。

产出：

- 一份 Markdown 文档（默认 `docs/research/YYYY-MM-DD-<topic>.md`，或用户指定路径）
- 图片保存在文档同级 `images/<topic>/`，文件名与章节对应；除 Mermaid 外，正文默认以 Markdown 链接引用**本地下载文件**，使用相对路径，不写绝对路径，也不直接用远程图片 URL 代替本地文件；用户要求预览可见时应使用相对路径内嵌图片
- 所有结论可追溯到来源；内部工作底稿记录内部信息出处与时间

## 硬性约束

1. **先澄清，后动笔。** 未完成澄清前不要产出正文。若用户明确说"按你的假设先写"，可以继续，但必须在文首列出假设并标注待确认项。
2. **章节固定为五章**：背景 / 现状 / 需求 / 方案 / 参考链接。前四章为正文，第五章只放来源链接、来源核验记录与图片版权说明；不要新增其他一级章节。节内可用二级标题（如"2.1 行业现状""2.2 华泰现状"）。第四章按用户决策类型二选一：
   - **选型模式**：用户要求比较多个候选方案时，标题用“方案选型”，按候选方案、评估维度与权重、评分对比、推荐结论、风险与验证计划展开，候选方案至少 3 个。
   - **方案模式**：用户已指定基础方案并给出总体链路时，标题可用“方案”，按总体设计、预验证/影响分级、上下文供给、多 Agent 审查、修复追踪与知识沉淀、集成与落地路径展开；仍须保留风险、验证计划与证据边界，不因“总体方案”省略可验证性。
3. **不要编造内部现状。** 华泰现状只能来自用户提供的材料或可查证信息；缺失处写"待补充/需确认"，并列出需要谁提供什么。
**公开稿不披露材料提供方式。** 研究底稿应保留“用户提供/内部材料”等来源属性、日期和责任人以保证审计追溯；面向公开分享的报告正文、图注、表格和参考目录不得出现“据用户提供”“用户提供的内部信息”等会暴露沟通/材料来源的措辞。公开来源应直接引用原始出版物；仅有内部依据的内容，先确认可公开范围，正文采用经确认的中性表述并标明“待核验/待补充”，或删除；不得将内部材料伪装成公开证据。
4. **尽可能多查网络**，并交叉验证；结论必须带来源。
5. **图片优先用现成的**：能下载的官方架构图/对比图必须保存到本地并保留来源与许可信息。默认情况下，除 Mermaid 外，截图、PNG/JPG/SVG 等一律用 `[图注](相对路径)` 链接写入正文，不写 `/Users/...` 等本机绝对路径。若用户明确要求在 Markdown 预览中直接看到图片，则改用内嵌图片 `![图注](相对路径)`，路径仍使用相对路径（如 `images/<topic>/xxx.png`）。只有下载失败时才使用远程外链，并明确标注“原图链接”。用户直接给出远程图片 URL 时也必须下载到本地并沿用相对路径规则，不得直接 hotlink；下载后用 `file`/`sips`/PIL 等方式识别真实格式（URL 后缀可能为 `.png` 但实际是 WebP），转换为合适格式后落盘，并在第五章“图片与版权”同步记录来源、获取日期和许可。若所用 Markdown→HTML 构建器不支持 Mermaid，架构图/流程图改用本地 SVG 自绘并标注“自绘”。
6. **先确认资讯来源，后正式撰写。** 完成初轮桌面研究后，先提交“本次资讯来源清单”并等待用户确认或明确授权；未确认前不得开始正文，除非用户明确要求跳过确认。清单至少写出来源类型、组织/项目、标题、URL、发布日期或访问日期、拟支撑的结论、交叉验证情况与置信度。研究底稿的来源清单须标注材料属性；公开稿按公开稿来源披露边界筛选和表述。
7. **行业实践固定覆盖六个实践簇**：阿里巴巴（含天猫、蚂蚁）、腾讯、字节跳动、Codex、Anthropic、其他实践。每个实践簇至少使用 2 个可追溯的有效来源，并同时检索 GitHub 高 star 项目和 QCon（优先 2026 上海及往届相关议题）。主题确实不适用时必须逐项写明“不适用”及原因，不能静默省略或用其他公司替代。不得虚构某公司未公开的 QCon 演讲；没有专属议题时，改用官方文档、GitHub 或明确的第三方采用证据。

8. **每个实践簇必须按统一五段展开**：在“二、现状”中，每个厂商/组织/项目实践都必须显式写出“背景、问题、方案、效果、规划”，并追加“局限与适用边界”。第 1 章的行业背景不能替代实践簇自己的背景与问题；“架构与编排”不能替代方案段；“量化结果/规模”不能替代效果段；缺少公开路线图时，规划段写“未公开/待确认”，不得省略或推测。

9. **五段内容必须逐字段有证据边界**：每个实践簇建立“字段—主张—来源—日期—置信度”记录。背景和问题说明采用动因、目标用户和触发场景；方案说明产品边界、部署形态、关键组件、集成与人机责任；效果优先记录 Code Review 相关指标（评审吞吐、等待时间、首条有效意见、可行动命中率、误报/漏检、采纳率、返工或缺陷逃逸）及口径、基线、时间范围、归因和证据等级（企业自报 / 公开基准 / 独立复现）；企业内部运行数据与公开 benchmark 结果不得混写为同一证据等级。规划区分“公开规划、报告建议、未知/待确认”。无法核验的字段必须明确标注“未公开/待确认”，不能用 stars、营销表述或推断填充。

**公开稿的统计说明位置。** 前四章正文不写成段的方法论免责声明，不出现“上述数字应按各自样本、变量定义和统计模型理解”“属于观察性研究中的关联信号”“不证明 AI 使用导致这些变化”“不同报告不能拼成因果链”等表述。正文按来源简洁呈现数据、事实及必要的“未公开/待确认”状态，并保留来源链接；样本、变量定义、统计模型、比较基线、相关/因果边界及不可横向比较等限定，统一记录在第五章“来源核验记录”或研究底稿证据字段。不得把多个来源组合成单一因果结论。

  使用 `references/research-playbook.md` 中的“实践簇五段证据矩阵”逐字段核对，不以“每簇两条来源”替代字段覆盖。

10. **代表性图片按实践簇配对**：有可复用的官方架构图、流程图、产品界面、部署图或原文实践图时，每个有直接证据的实践簇至少选择 1 张与该簇五段内容直接相关的本地图片；图片不足时使用自绘架构/证据流程图并标注“自绘”，或写“暂无可公开复用图片”并保留原文链接。不得用 logo、通用装饰图或同一张图冒充多个厂商证据。图片必须有图注、来源、获取日期、许可说明，并能在“图片—实践簇—主张”之间回溯。

11. **用户点名的厂商优先于默认矩阵**：若用户指定了不同厂商、项目或实践簇，保留用户指定集合并说明与默认六簇的映射、增删和原因；默认六簇仅在用户未指定范围时补充使用。不能为了满足固定矩阵把用户对象塞入“其他”或编造不适用结论。

12. **技能维护请求单独处理**：用户要求“修改/同步 skill”时，先检查主 `SKILL.md` 与其引用的模板、清单、研究手册，再同步修改相关文件；验证交叉文件的一致性，并在交付中列出修改文件和验证结果。仅修改 skill 指令时，不因报告写作 Gate 强制重新询问调研来源；若同时要求改报告，报告仍遵循来源确认 Gate。

## 工作流

### 1. 澄清（Gate）

一次性提出 5-8 个关键问题（不要挤牙膏式逐条问），覆盖：

- 调研主题与要解决的业务/技术问题
- 决策类型与读者（立项/选型/替换/自研 vs 采购；是“多方案选型”还是“基于指定基础方案写总体落地方案”）
- 范围边界（部署形态、规模、合规、现有技术栈）
- 华泰现状与可提供的内部材料（仅用于研究核验；公开稿披露前确认授权范围）
- 输出要求（篇幅、格式、是否要图、时间点）
- 否决项/成功标准

问题清单与"最小澄清集"见 [references/clarification-checklist.md](references/clarification-checklist.md)。

### 2. 桌面研究与来源确认

按 [references/research-playbook.md](references/research-playbook.md) 执行：来源优先级、检索式、行业实践来源矩阵、GitHub 评估清单、QCon 探索和证据表。已确认的候选来源池见 [references/industry-source-baseline.md](references/industry-source-baseline.md)，使用前必须复核时效性。

#### 2.1 按矩阵检索

- 按六个实践簇分别检索：阿里巴巴（含天猫、蚂蚁）、腾讯、字节跳动、Codex、Anthropic、其他实践
- 每个实践簇至少收集 2 个可追溯来源；优先“1 个一手来源 + 1 个独立验证”
- GitHub 检索同时查看 star、近 6 个月活跃度、release、issue/PR、license 和生产案例；star 只作发现信号，不作技术结论
- QCon 2026 上海议程：<https://qcon.infoq.cn/2026/shanghai/schedule>；必要时回溯往届或其他城市。QCon 是生产经验来源，关键结论仍需官方文档、GitHub 实现或第二个独立来源验证
- Codex、Anthropic 等没有对应 QCon 专属议题时，不得拼凑或误标；使用官方文档、GitHub 与明确的第三方采用证据
- 每个实践给出：组织/产品与场景、架构与编排、关键能力、量化结果或规模、局限、成熟度、成本、与本议题的相关性
- 每个实践必须使用以下字段顺序：**背景 → 问题 → 方案 → 效果 → 规划 → 局限与适用边界**；逐字段记录证据、日期和置信度。规划不得从当前架构外推，未知就写“未公开/待确认”。
- 先列出“实践簇清单”，区分厂商、产品和子实践（例如阿里巴巴下的淘天/天猫、蚂蚁、开源项目）；除非有明确理由，不得把多个对象合并成一个“其他”条目。每个清单项都要完成六字段覆盖和图片/无图说明。
- 对 AI Code Review 主题，效果字段优先回答评审吞吐、等待时间、首条有效意见、可行动命中率、误报/漏检、采纳率、返工/缺陷逃逸和人工复核负担；只有通用 Agent 指标时必须说明与 Code Review 的相关性有限。

#### 2.2 来源清单确认（Gate）

初轮检索完成后，先用 [research-playbook.md](references/research-playbook.md) 的「来源清单确认模板」向用户提交本次来源清单，等待用户确认、删减或补充后再撰写正文。

- 研究底稿清单可包含用户提供的材料；与公开检索结果统一编号并记录来源属性。对外版清单不披露材料提供方式，仅列可公开引用的来源；内部材料需先确认公开授权，未获授权不得进入公开版来源目录。
- 用户确认后，新发现的有效来源仍可补充，但不得静默替换已确认的实践簇；最终全部列入第五章
- 确认记录写入第五章“来源核验记录”，包括确认日期和用户提出的增删要求

#### 2.3 证据整理

- 至少 2 个独立来源交叉验证关键数字；记录版本与访问日期
- 一手官方资料优先；QCon 用于生产经验，GitHub 用于实现与生态，第三方报告只作背景
- 事实、推断、建议分开记录；无法确认的内容标为“待确认”

### 3. 撰写正文四章与参考链接

模板见 [references/document-template.md](references/document-template.md)。

- **一、背景**：技术/产品演进脉络，或当前问题的量化描述（现状指标、痛点、触发事件）。
- **二、现状**：行业现状固定按六个实践簇展开（阿里巴巴含天猫与蚂蚁、腾讯、字节跳动、Codex、Anthropic、其他实践）+ 对比表，再写华泰现状。每个簇至少 2 个已确认来源，并按“背景 / 问题 / 方案 / 效果 / 规划 / 局限与适用边界”六段写作；确实不适用时仍保留六段标题并逐项说明“不适用”及证据原因。每个有直接证据的簇至少配 1 张代表性图片或明确记录“暂无可公开复用图片”。
- **三、需求**：功能点 + 用户场景（角色/触发/流程/成功标准），区分 P0/P1/P2 与非功能约束。
- **四、方案 / 方案选型**：选型模式至少 3 个候选方案（含自研/采购/开源），统一维度打分，给出推荐结论、风险与验证计划；方案模式以已指定基础方案为内核，按总体设计、预验证、影响分级、上下文供给、多 Agent 审查、修复追踪与知识沉淀、集成与落地路径展开，并保留风险、验证计划和证据边界。推荐结论或总体方案都必须放在第四章内，不要另起一章。
- **五、参考链接**：按六个实践簇、可公开引用的补充材料、图片与版权、来源核验记录分组，集中列出全部公开来源和访问日期；内部材料来源属性仅留在研究底稿，不进入公开版参考目录。正文保留内联引用，但不再在各章末尾重复列来源。
- **多轮编辑**：修改已有 Markdown 前先重新读取目标段落；用户可能手动改过文档，用章节标题或段落边界定位整段替换，不要基于上一轮缓存打补丁。

### 4. 图表

- **图注格式**：每张图（含 Mermaid 和截图）必须有 `图 <章节号>-<序号>：<标题>` 形式的图注；章节号取图所在最小小节编号（如 2.1.2），序号在该小节内从 1 递增。例：`图 2.1.2-1：Multica 总体架构（自绘）`
- **Mermaid 图**：直接写在 Markdown 的 `mermaid` 代码块中，使其在文档内渲染；图注标明"自绘"
- **Mermaid 兼容性**：若所用 Markdown→HTML 生成器不支持 Mermaid，不要写 `mermaid` 代码块；改用本地 SVG 自绘图并在图注标注“自绘”。
- **重排与清理**：小节增删或重排后，图注按新的最小小节号重算；删除正文内容时同步清理第五章来源与孤儿图片引用。
- **其他图片**（官方架构图、对比图、PNG/JPG/WebP/SVG 截图等）：保存到 `images/<topic>/`。默认写**本地相对路径链接**，例如 `[图 2.1.2-1：XXX 架构图（PNG）](docs/research/images/<topic>/xxx.png)`；若用户要求预览可见，则写内嵌图片 `![图 2.1.2-1：XXX 架构图（PNG）](images/<topic>/xxx.png)`。两者都不要写绝对路径，也不要把官方远程图片 URL 当作默认链接
- 每张图的来源链接、获取日期、许可（如适用）统一写入第五章“参考链接”的图片与版权部分
- 无法下载时保留外链与图注，不要用凭空生成的图替代事实图

### 5. 质量自检（交付前）

- [ ] 五个一级章节齐全：背景 / 现状 / 需求 / 方案（或方案选型）/ 参考链接，没有未经确认的其他新增章节
- [ ] 第四章模式与用户要求一致：选型模式至少有 3 个候选并评分；方案模式已明确基础内核、各阶段职责、风险与验证计划
- [ ] 修改“现状/流程/能力”类事实后，已全库搜索同类表述，背景、导语、表格与摘要同步更新，无新旧口径并存
- [ ] 若存在 MD→HTML 等文档构建脚本，已重跑构建并校验标签闭合与图片相对路径可解析
- [ ] 所有来源已统一放入第五章“参考链接”，前四章没有“本章来源”或分散来源清单
- [ ] 已设置并完成“资讯来源清单确认”Gate；有确认日期和用户增删意见记录
- [ ] 行业现状覆盖六个实践簇：阿里巴巴（含天猫、蚂蚁）、腾讯、字节跳动、Codex、Anthropic、其他实践；每簇至少 2 个来源，或明确说明不适用
- [ ] GitHub 高 star 项目和 QCon 2026 上海均已检索；Codex、Anthropic 无专属 QCon 议题时没有虚构或误标
- [ ] 关键数字有出处、有日期、有版本
- [ ] 每个实践簇均有“背景 / 问题 / 方案 / 效果 / 规划 / 局限与适用边界”六段，不能用行业总述替代
- [ ] 每个实践簇的五段字段均有来源或明确写“未公开/待确认”；效果包含口径、基线、时间范围与归因边界

## 写作风格

## 公开稿来源披露边界

公开分享版不得写“据用户提供”“用户提供的内部信息”“内部材料显示”等暴露沟通来源的表述，也不得在参考目录、图注、表格或核验记录中标记某项公开来源是由用户提交。工作底稿必须保留真实来源属性、日期与责任人，不能为了公开展示而丢失审计链。公开来源直接以机构/作者/报告名称引用；只有内部依据的事实，先确认公开授权，再决定采用中性且获准的陈述、标注待核验/待补充或从公开稿删除。不得将内部信息包装成公开来源或独立验证结论。

## Skill 维护请求

当用户要求修改或同步本 skill 时，先检查 `SKILL.md` 及其引用的模板、清单和研究手册，再同步修改相关文件；验证交叉引用、章节约束、字段矩阵和质量检查项一致，并在交付中列出修改文件和验证结果。纯 skill 指令修改不需要重新执行报告来源确认 Gate；同一请求若同时要求改报告，报告部分仍遵循来源确认 Gate。

- 架构师口吻：先结论后论据，避免营销形容词
- 能量化就量化（QPS、规模、延迟、成本、人力）
- 区分"事实/推断/建议"；推断注明依据
- 引用格式：正文内联 `[来源](URL)`；全部来源统一汇总到第五章“参考链接”，不要在各章末尾重复列出来源
- 篇幅未指定时，默认 3000-5000 字；先给结论摘要，再逐章展开
